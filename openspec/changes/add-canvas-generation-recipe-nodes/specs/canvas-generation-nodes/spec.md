## ADDED Requirements

### Requirement: Canvas has one canonical Generation Node contract

Canvas SHALL define one canonical `generation` node with a strict `prompt`, `image`, `audio` or `video` Recipe union. The node SHALL persist editable Recipe facts, exact run/output relationships and current output selection in `.nkc`, while GenerationJob state, provider tasks, generated bytes and Asset facts remain owned by their respective domains.

#### Scenario: A Generation Node is saved and reopened

- **WHEN** a user configures a Generation Node, saves the Canvas and reopens the exact document
- **THEN** the same Recipe, stable run/output references and current output selection are restored
- **AND** no schema version, provider credential, runtime URL, raw path, process handle or copied Job phase is stored in the node

#### Scenario: An imported asset is placed on Canvas

- **WHEN** a user drags or imports an existing image, audio or video asset
- **THEN** Canvas creates an ordinary Media Node without Generation Recipe authority
- **AND** it does not infer a Recipe from asset metadata, filename or prior generation provenance

### Requirement: Generation Node runs use exact typed authoring state

Running a Generation Node SHALL require exact Workspace, Canvas document/session, node, request and current document identity. Canvas SHALL validate the Recipe and resolve explicit connected inputs before submitting one typed request to the exact Workspace GenerationJob owner.

#### Scenario: A configured node is run

- **WHEN** the user explicitly runs a valid Generation Node with an available purpose-qualified model
- **THEN** Canvas snapshots the current Recipe and authorized inputs, persists one run request identity and submits one matching GenerationJob
- **AND** Generation returns one canonical JobRef without creating a Conversation, Agent Turn, Tool Call or second Canvas Job owner

#### Scenario: A stale Canvas identity submits a run

- **WHEN** a request carries a stale document revision, mismatched session/node identity or unavailable model binding
- **THEN** only that run is rejected with an owner-qualified diagnostic
- **AND** no Job, provider request, active/recent Canvas fallback or sibling-node mutation occurs

### Requirement: Generation submission is idempotent across persistence boundaries

Canvas SHALL persist a stable submission request identity before external execution, and Generation SHALL map equivalent repeats of that identity within the exact Workspace to one JobRef. Reusing the identity with a different request payload SHALL fail visibly.

#### Scenario: Desktop restarts after Job creation but before JobRef binding

- **WHEN** Canvas recovers a persisted run request whose provider submission outcome is uncertain
- **THEN** it resubmits or reconciles the same request identity and obtains the original JobRef or an explicit unknown-outcome diagnostic
- **AND** it does not create a second paid provider operation or mark the run successful without a canonical Job

#### Scenario: A submission identity is reused with changed input

- **WHEN** a caller submits the same request identity with a different Recipe, input fingerprint, provider or model
- **THEN** Generation rejects the conflict
- **AND** it does not overwrite, alias or retry the original Job through another executor

### Requirement: Generation Node inputs are explicit and typed

Canvas SHALL resolve only the node’s own Recipe and explicitly connected typed inputs. Text inputs SHALL be snapshotted with stable content evidence, and media inputs SHALL resolve to authorized ContentLocators before Job submission.

#### Scenario: Prompt and reference inputs are valid

- **WHEN** a Generation Node has compatible connected text and media sources with stable content identity
- **THEN** Canvas builds the kind-specific request from those exact inputs
- **AND** the Job request contains no Canvas runtime URL, blob/data URL, cache path, raw filesystem path or active selection

#### Scenario: A connected input is unavailable

- **WHEN** an upstream Generation Node has no selected successful output or a connected input has the wrong type, stale identity or unauthorized locator
- **THEN** the current run fails before Job submission with an input-local diagnostic
- **AND** valid sibling nodes and existing outputs remain usable

### Requirement: Successful results fill the originating Generation Node

A terminal successful GenerationJob SHALL commit durable outputs before Canvas applies them to the exact originating Generation Node. Result apply SHALL append output bindings and select the newest output without creating default Job, Media, File or Group sibling nodes.

#### Scenario: One output completes successfully

- **WHEN** the active run commits one valid output locator
- **THEN** Canvas atomically attaches that locator and JobRef to the originating node and displays it as the selected output
- **AND** no Workspace Board mirror or separate result node is created

#### Scenario: Multiple outputs complete successfully

- **WHEN** one Job commits multiple valid outputs
- **THEN** all outputs become selectable history within the same Generation Node
- **AND** the node exposes exactly one selected output to downstream connections without creating an automatic Canvas Group

#### Scenario: Result apply target is no longer valid

- **WHEN** the originating node was deleted, a different run owns it or the exact document cannot safely apply the result
- **THEN** Canvas blocks only the apply and exposes a diagnostic while the committed artifact remains durable
- **AND** it does not recreate the node, select another Canvas or fall back to a Media Node

### Requirement: Reruns preserve output history and user selection

Every explicit rerun SHALL create a new GenerationJob and new immutable outputs. Canvas SHALL preserve prior output bindings and SHALL NOT overwrite or delete an existing artifact when selecting a newer or older output.

#### Scenario: A node is rerun successfully

- **WHEN** a Generation Node with a selected output completes a later run
- **THEN** the prior output remains available in node history and the new output becomes selected
- **AND** both outputs retain their exact Job and content identities

#### Scenario: A rerun fails or is cancelled

- **WHEN** a later run fails or is cancelled
- **THEN** the previous successful output remains visible and selected
- **AND** the failed Job diagnostic is displayed on the same node without reporting result success

#### Scenario: Recipe changes during a run

- **WHEN** the user edits the Recipe after the active Job request was captured
- **THEN** the terminal output remains bound to its submitted Recipe/input fingerprint and is preserved
- **AND** Canvas visibly indicates that the current Recipe differs from the selected generated result

### Requirement: One node has at most one active run

The first release SHALL allow at most one non-terminal GenerationJob per Generation Node. It SHALL NOT automatically run a node because an upstream value, connection, output selection or Recipe changed.

#### Scenario: User runs a node while its Job is active

- **WHEN** the same node already has a pending, running or unknown-outcome Job
- **THEN** Canvas rejects the second run and exposes cancel or wait actions
- **AND** it does not queue a hidden run or reuse the active Job with changed inputs

#### Scenario: An upstream result changes

- **WHEN** an upstream node selects another result or edits connected text
- **THEN** the downstream Recipe remains idle until the user explicitly runs it
- **AND** no provider call or cost-producing operation starts automatically

### Requirement: Generation runs survive UI lifecycle without owning user records

GenerationJob execution SHALL survive Canvas renderer unmount, View closure and navigation according to Workspace Job lifecycle. Reopening the document SHALL reattach to the exact persisted run identity and JobRef without selecting an active/recent Workspace or duplicating work.

#### Scenario: Canvas closes while a Job runs

- **WHEN** the package-owned Canvas Root unmounts during a non-terminal run
- **THEN** the Workspace GenerationJob may continue without retaining the React tree
- **AND** reopening the exact document reconstructs node status from Canvas run binding and authoritative Job observation

#### Scenario: One persisted run binding is invalid

- **WHEN** one node contains a missing, malformed or unresolvable run/output reference
- **THEN** that node keeps its Recipe and valid sibling outputs while displaying a local repair diagnostic
- **AND** the Canvas document, sibling nodes, other Workspaces and application remain usable

### Requirement: Prompt and media outputs use appropriate node presentation

Prompt/Text Generation Nodes SHALL render generated text content, and Image/Audio/Video Generation Nodes SHALL render their selected media through authorized package-owned preview paths. Editing generated text SHALL preserve the immutable generated source artifact and provenance.

Canvas SHALL present selected content as separate action, node-content and Generation-input layers. The existing selection action toolbar SHALL remain independent of the node. A selected Generation Node SHALL render its Recipe editor in a separate package-owned input panel, while the durable node renders only type/status and current content or generated output. Ordinary imported or referenced nodes SHALL NOT display the Generation input panel.

#### Scenario: Prompt generation succeeds

- **WHEN** a Prompt GenerationJob commits a durable text output
- **THEN** the originating node displays the generated text and exposes text to downstream typed connections
- **AND** ordinary Agent transcript text is not imported or treated as the Job result

#### Scenario: User edits generated text

- **WHEN** the user explicitly edits text derived from a selected generated output
- **THEN** Canvas creates Canvas-owned authored text state linked to the immutable source output
- **AND** it does not rewrite the generated artifact or fabricate a new provider Job

#### Scenario: A Generation Node is selected before generation

- **WHEN** one Prompt, Image, Audio or Video Generation Node is the exact selection
- **THEN** Canvas shows the selection action toolbar, the content node and one detached Generation input panel
- **AND** the input panel edits the same node's prompt, connected-reference summary, exact model and legal kind-specific parameters without creating another Canvas node

#### Scenario: Generation completes while the node remains selected

- **WHEN** the selected Generation Node receives a successful committed output
- **THEN** the output fills the content area of the same node
- **AND** the detached input panel remains available for an explicit rerun without covering or resizing the node content

#### Scenario: A referenced content node is selected

- **WHEN** the exact selection is an ordinary imported or referenced Media, Markdown or File node
- **THEN** Canvas shows its selection actions and content node
- **AND** it does not show a Generation Recipe input panel or infer generation authority from provenance

### Requirement: Canvas mutations preserve user-observed command order

All Webview-originated mutations of one Canvas Host session SHALL enter one serial command stream, including whole-document status replacement and narrow Generation/source/material intents. A later narrow intent SHALL execute against the authoritative result of every earlier queued document mutation and SHALL NOT restore content deleted by those mutations.

#### Scenario: User deletes content and immediately adds a Generation Node

- **WHEN** the Webview submits a document state that removes a node and then requests a Generation Node
- **THEN** Host commits the deletion before creating the new node
- **AND** the returned and projected snapshot contains the new Generation Node but not the deleted node or its connections

#### Scenario: A local command projection is observed

- **WHEN** Host emits the monotonic projection event for a locally queued mutation
- **THEN** the Webview Host treats it as acknowledgement of the same ordered command stream
- **AND** it does not publish an older snapshot as a competing success path or merge stale nodes back into the document

### Requirement: Historical Canvas content remains visible without a parallel regenerate path

Existing Markdown, Media, File and Job nodes SHALL remain readable and editable according to their canonical node contracts. New Generation authoring SHALL NOT continue the historical material-result regenerate path that creates another Job/Media graph.

#### Scenario: A historical generated Media Node is opened

- **WHEN** an existing Canvas contains a Media Node with Generation provenance but no Generation Recipe node
- **THEN** the media and provenance remain visible
- **AND** regeneration requires an explicit new Generation Node using that material as input rather than invoking the removed parallel path
